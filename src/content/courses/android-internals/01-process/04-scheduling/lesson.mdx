## The question

Your app has about forty threads. The phone is running two hundred processes,
and most of those have threads of their own. Call it a few thousand.

The phone has eight cores.

Two things everybody says, which cannot both be simple:

> Don't create too many threads, it's expensive.
>
> Coroutines are lightweight, you can have thousands.

Coroutines run on threads. If threads are expensive, how does putting ten
thousand coroutines on them make anything cheaper?

What most developers picture:

```text
40 threads
   ↓
40 things happening at once
```

What is actually happening:

```text
8 cores, 8 threads running
   ↓  everything else waits
the scheduler picks who is next
   ↓  a turn ends
save registers, load the next
   ↓
another thread runs
```

## What is actually happening

### A core runs exactly one thread

Not mostly one. One. Eight cores means eight threads are executing at this
instant, and every other thread in every app on the phone is waiting.

Everything that looks like more than eight things happening is the kernel
switching between them faster than you can see.

### The scheduler decides who runs

The kernel keeps a list of every thread that is ready to run, across every
process, and picks which ones get the cores. That component is the
**scheduler**.

It schedules threads, not processes. Your app's threads sit in the same list as
every other app's, and your process gets attention in proportion to the threads
it has ready and how important the system thinks they are.

### A context switch is the handover

To take a thread off a core and put another one on, the kernel has to save
where the first one was: its CPU registers, the program counter that says which
instruction is next, and the stack pointer. Then it loads the same things for
the incoming thread.

That is a **context switch**. It is not free, and nothing useful happens during
it.

### Switching to another process costs more than switching to another thread

Two threads in one process share an address space, so the page table from
lesson 1.2 stays exactly as it was. The kernel swaps registers and carries on.

Switching to a thread in a *different* process means switching page tables too,
and the processor's cached translations from the old table stop being useful.
So the same operation costs noticeably more.

That is the real reason threads are described as cheaper than processes. It is
not a slogan. It is one table that does not have to change.

### Which makes both of those sayings true at once

Ten thousand threads is bad for two separate reasons. Each thread needs a stack
reserved for it, and each one joins the scheduler's list, so the kernel spends
its time switching rather than running anything.

A coroutine is not in that list. The scheduler has never heard of it. It is an
object on your heap, and when it suspends it occupies no thread at all. A
dispatcher keeps a small pool of real threads and runs whichever coroutines are
ready on them.

Think of the cores as eight stoves in a kitchen. Threads are pots, and only
eight can be on the heat. The analogy stops exactly where it gets interesting:
a pot cannot be taken off the stove, set down with its state intact and resumed
later at no cost, and that is precisely what a suspended coroutine does.

This is why the main thread from the last lesson freezes everything when it is
busy: it is one thread, its turn is being used by your slow call, and no other
core can take work that is not allowed to move.

## Connect it to your code

Two loops that look similar and are not.

```kotlin
// the operating system makes ten thousand of its own objects
repeat(10_000) {
    thread { Thread.sleep(1_000) }
}
```

```kotlin
// ten thousand objects on your heap, a handful of real threads
repeat(10_000) {
    scope.launch { delay(1_000) }
}
```

The first asks the kernel for ten thousand stacks and ten thousand entries in
the scheduler's list. The second asks for ten thousand small objects and, while
they are all suspended, no threads at all.

> A thread is an operating system object with a stack and a place in the
> scheduler's queue. A coroutine is an object on your heap. The scheduler has
> never heard of it.

What each dispatcher is really giving you:

| Dispatcher | The pool behind it | Use it for |
|---|---|---|
| `Dispatchers.Default` | about as many threads as the device has cores | work that keeps a core busy |
| `Dispatchers.IO` | a larger pool, because these threads are expected to sit blocked | waiting on files, sockets, databases |
| `Dispatchers.Main` | exactly one thread, the one from the last lesson | touching the UI, and nothing slow |

`Dispatchers.IO` is larger on purpose: a thread blocked on a socket is not using
a core, so having more of them costs little. Putting heavy computation there
instead of on `Default` gives you many threads all wanting cores at once, which
is the thrashing this lesson describes.

## When it breaks

**Too many threads, and the failure names the stack.**

```console
java.lang.OutOfMemoryError: pthread_create (1040KB stack) failed: Try again
```

Notice what ran out. Not your heap: the memory reserved for one more thread's
stack. A thread pool with no bound, or a library creating a thread per request,
gets here on a phone long before it would on a server.

**Heavy computation on the wrong dispatcher.**

Moving processing to `Dispatchers.IO` because it felt like "not the main
thread" puts dozens of compute-hungry threads in the scheduler's list at once.
Everything gets slower, including the main thread, and the profile shows time
spent switching rather than working.

## Your notes

```text
8 cores  =  8 threads running, right now
        ↓
scheduler: one list of ready THREADS
           from every process
        ↓  a turn ends
CONTEXT SWITCH
  save registers, program counter,
  stack pointer; load the next
        ↓
same process?  page table stays  → cheap
other process? page table swaps  → costly

coroutine = object on your heap
the scheduler never sees it
suspended = holding no thread
```

- A core runs one thread at a time. Everything else is waiting.
- The scheduler picks from one list of ready threads across all processes.
- A context switch saves and restores registers, the program counter and the
  stack pointer.
- Switching between processes also swaps the page table, so it costs more.
- Ten thousand threads means ten thousand stacks and a kernel busy switching.
- A coroutine is not a scheduler object, and a suspended one uses no thread.

## Interview questions

Answer out loud first, then open the model answer.

**1. (Easy)** How many threads can a phone with eight cores run at the same
moment?

<details>
<summary>Model answer</summary>

**Hit these points**

- Eight, one per core.
- Every other ready thread on the device is waiting for a turn.
- The appearance of more is the kernel switching between them quickly.
- That number is shared across every app, not per app.

**A weak answer** says "as many as you create", which confuses threads existing
with threads running.
</details>

**2. (Easy)** Does the Linux scheduler schedule processes or threads?

<details>
<summary>Model answer</summary>

**Hit these points**

- Threads. A process runs because its threads are scheduled.
- All ready threads across all processes are in one list.
- So a process with more ready threads competes for more of the cores.
- Priority also weighs in, which is how foreground work stays responsive.

**A weak answer** says processes, which makes the rest of the model wrong: it
cannot then explain why a thread switch is cheaper than a process switch.
</details>

**3. (Medium)** What is saved during a context switch, and why is switching
between two processes more expensive than between two threads?

<details>
<summary>Model answer</summary>

**Hit these points**

- The CPU registers, the program counter and the stack pointer of the outgoing
  thread, then the same values loaded for the incoming one.
- Two threads in one process share an address space, so the page table is
  untouched.
- Two threads in different processes need the page table swapped as well.
- The processor's cached address translations also stop being useful, so the
  first accesses after the switch are slower.

**A weak answer** says process switches are "heavier" without naming the page
table, which is the actual difference.
</details>

**4. (Medium)** Why is creating ten thousand threads a bad idea?

<details>
<summary>Model answer</summary>

**Hit these points**

- Each one reserves a stack, so the memory cost is real before any of them run.
- Each one joins the scheduler's list, so the kernel spends more time switching
  and less running.
- Only as many as there are cores can make progress at any instant anyway.
- The failure when it comes is usually an out-of-memory error naming a thread
  stack rather than the heap.

**A weak answer** says "too many threads is slow" without separating the memory
cost from the switching cost.
</details>

**5. (Hard)** Coroutines run on threads. So how can ten thousand coroutines be
cheaper than ten thousand threads?

<details>
<summary>Model answer</summary>

**Hit these points**

- A coroutine is an object on the heap, not an operating system object.
- It is never in the scheduler's list, so it adds nothing to switching costs.
- When it suspends, it holds no thread at all: its state is kept in an object
  and the thread goes and runs something else.
- A dispatcher keeps a small pool of real threads and runs whichever coroutines
  are ready on them.

**A weak answer** says coroutines are lightweight because they are not threads,
which is true and not an explanation. The mechanism is suspension releasing the
thread.
</details>

**6. (Hard)** A developer moves image processing from `Dispatchers.Default` to
`Dispatchers.IO` because the app feels slow. What happens?

<details>
<summary>Model answer</summary>

**Hit these points**

- The IO pool is deliberately much larger, because its threads are expected to
  be blocked and not using a core.
- Compute work does use a core, so now many threads want cores at once.
- The scheduler spends more time switching, and the main thread waits longer
  for its turn as well.
- `Default` is sized near the core count precisely to avoid this.

**A weak answer** treats the two dispatchers as interchangeable ways of leaving
the main thread, which is the assumption that caused the problem.
</details>

**7. (The one that matters)** Explain why coroutines are lightweight, to an
interviewer, in four sentences.

<details>
<summary>Model answer</summary>

A core can run one thread at a time, and the kernel's scheduler keeps a list of
every ready thread on the device and takes turns between them, saving and
restoring registers on each switch. A thread is an operating system object: it
reserves a stack and it joins that list, so thousands of them cost memory and
make the kernel spend its time switching. A coroutine is an object on my heap
that the scheduler has never heard of, and when it suspends it stores its state
in that object and releases the thread entirely. So a dispatcher can run many
thousands of coroutines over a small pool of real threads, and the operating
system only ever sees the pool.
</details>

## Words you met

| Term | What people say | What it actually means |
|---|---|---|
| Core | "the CPU" | One execution unit of the processor. It runs exactly one thread at any instant. |
| Scheduler | "the OS decides" | The kernel component that keeps one list of every ready thread on the device and chooses which get the cores. |
| Context switch | "the OS switches tasks" | Saving the outgoing thread's registers, program counter and stack pointer and loading the incoming one's. Across processes it also swaps the page table. |
| ANR | "the app crashed" | Application Not Responding: the system reporting that the main thread did not get to something waiting for it. Nothing threw. [ANRs](https://developer.android.com/topic/performance/vitals/anr) |

## Why a Bundle has a size limit

**You will:** cause `TransactionTooLargeException` on purpose, explain where the limit comes from, and fix it.
**You need:** an Activity with a button, and a second Activity to open.
**Time:** about 15 minutes.
**Built with:** compileSdk 36, AGP 8.13, Kotlin 2.3.

### The problem you can see

Open a second screen and attach two megabytes to the intent:

```kotlin
// MainActivity.kt
Button(onClick = {
    startActivity(
        Intent(this, DetailActivity::class.java)
            .putExtra("payload", ByteArray(2_000_000))
    )
}) { Text("Open detail") }
```

Tap it.

```
java.lang.RuntimeException: android.os.TransactionTooLargeException: data parcel size 2000xxx bytes
```

(The last digits are your array plus a little packaging, so they vary.) Nothing in Kotlin forbids a two-megabyte array. The rule is not in your code.

### What is actually happening

`startActivity` does not start anything by itself. Your process is not allowed to. It sends a request to a different process called **`system_server`**, the one system process that runs Android's core services: which screen is showing, which apps are installed, what notifications exist.

Your process cannot reach into `system_server`'s memory, so Android copies the request across. It packs your Intent, extras included, into bytes and hands them to a part of the operating system called **Binder**, which copies them into the other process and waits for the answer. Every request your app makes to the system goes this way.

Here is the limit. Each process gets about **1 MB** of space for these copies, and every request it is making at the same moment shares that space. Two megabytes can never fit. Seven hundred kilobytes might fit today and fail tomorrow, because something else was in flight. The official [`TransactionTooLargeException`](https://developer.android.com/reference/android/os/TransactionTooLargeException) page states the 1 MB figure and gives the real guidance: keep intent extras to a few kilobytes, and saved state under 50 KB.

Saved state from lesson 1 crosses the same way, to the same place. That is why a `Bundle` has a size limit, and why it is the same limit everywhere.

### Fixing it, step by step

#### Step 1: shrink it and watch the limit move

Change `2_000_000` to `200_000`. Run it.

**What you should see:** no crash.

**Why:** 200 KB fits. It is still far above the "few kilobytes" the docs recommend, and it still shares space with everything else. This is a demonstration, not a fix.

#### Step 2: send a key, not the data

Keep the data in your own process and send only a short id:

```kotlin
// Payloads.kt
object Payloads {
    private val store = mutableMapOf<String, ByteArray>()
    fun put(id: String, bytes: ByteArray) { store[id] = bytes }
    fun get(id: String): ByteArray? = store[id]
}

// MainActivity.kt
Payloads.put("article-42", ByteArray(2_000_000))
startActivity(Intent(this, DetailActivity::class.java).putExtra("payloadId", "article-42"))

// DetailActivity.kt
val bytes = Payloads.get(intent.getStringExtra("payloadId")!!)
```

**What you should see:** the detail screen opens with all two megabytes available.

**Why:** only a short string crossed to `system_server`. Both Activities live in the same process, so the data never had to move.

<Callout kind="warn" title="You already know the hole in this fix">
`Payloads` is an object in memory. Lesson 1 showed what happens to objects in memory: press Home on the detail screen, run `am kill`, come back, and `Payloads.get` returns null. Passing an id is the right pattern. Where the data waits for you is a chapter 5 and chapter 15 question. This shortcut is deliberate, and you will replace it later.
</Callout>

### When it breaks

**The crash happens when the user leaves, not when they tap.** Same exception, with `onSaveInstanceState` in the stack, and often this line in logcat:

```
!!! FAILED BINDER TRANSACTION !!!  (parcel size = 2000xxx)
```

Something large was put in saved state, and saved state is sent to `system_server` when the screen stops. Save an id and reload the data (chapter 5).

**Works for weeks, then crashes on one screen.** The data was small in testing and grew with real users. Never put a list of model objects into an intent or saved state.

**An ANR whose top frame is `android.os.BinderProxy.transactNative`.** Your code is not slow. It is waiting for `system_server`, which is busy. Chapter 12 covers what to do.

### Try it yourself

Before you run it: put the two-megabyte array into saved state instead of an intent.

```kotlin
val payload by rememberSaveable { mutableStateOf(ByteArray(2_000_000)) }
```

Predict: does it crash when the screen appears, when you tap something, or at some other moment?

**Answer:** at some other moment. The screen appears fine, because `rememberSaveable` only holds the value. Press Home or rotate and it crashes, because that is when the saved state is copied to `system_server`. The failure happens wherever the bytes cross, not where you created them.

### Words you met

**`system_server`**: the one system process that runs Android's core services, including the one that opens and closes your screens. [Platform architecture](https://developer.android.com/guide/platform)

**Binder**: the part of Android that copies a request from one process to another and brings the answer back. [Binder overview](https://source.android.com/docs/core/architecture/ipc/binder-overview)

**`TransactionTooLargeException`**: the error when a request does not fit in your process's 1 MB of shared Binder space. [Reference](https://developer.android.com/reference/android/os/TransactionTooLargeException)

<Callout kind="note" title="Go deeper (optional)">
Every "manager" the framework hands you works this way. `ActivityManager`, `WindowManager`, `PackageManager` and `NotificationManager` are all small local objects that forward your calls to `system_server` over Binder; putting your window on the screen is done by yet another process, `SurfaceFlinger` (chapter 8). So when a framework call surprises you, ask: *which process does this run in?* If the answer is "not mine", it can be slow, it can fail for reasons you did not cause, it has a size limit, and the answer was true when it was copied rather than now. That one question resolves a large share of Android confusion, and chapters 12 and 11 lean on it.
</Callout>

## Process priority &amp; the OOM killer

Start with the mechanism, because everything else is downstream of it.

Android runs on Linux with limited RAM and no swap. When memory runs low something must die, and the kernel's low-memory killer picks by **`oom_adj`** — a score the system assigns each process. Higher score, killed sooner.

`system_server` (ch. 2) sets that score from what your app is currently doing:

| Bucket | Your app | Killed |
|---|---|---|
| Foreground | a visible Activity, or a foreground service | almost never |
| Visible | visible but not focused — split screen (ch. 5) | rarely |
| Service | a running background service | when memory is tight |
| Cached | nothing running; kept in case the user returns | **first, freely, silently** |
| Empty | no components at all | immediately |

**Priority is earned, not requested.** There is no API to say "please keep me". You move up the ladder by doing something the user can see — showing a screen, posting a foreground-service notification. That is the entire contract, and it is why the platform's answer to "how do I keep running" is always "show the user something".

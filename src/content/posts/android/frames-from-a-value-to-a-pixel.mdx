Chapter 12 gave you the deadline: 16.6 ms, on a queue shared with everything else. This chapter is what has to happen inside it.

The value of knowing this pipeline is that jank stops being mysterious. "The list stutters" becomes "the layout pass is running for every item because a `requestLayout` is walking to the root" — a sentence with a fix in it. And the pipeline is the same underneath Views and Compose, which is why this chapter sits before both.

## Looper, Handler, MessageQueue

The primitive is older than every framework built on it, and it is worth seeing plainly because everything else is a wrapper.

A thread with a **`Looper`** runs an infinite loop pulling messages off a **`MessageQueue`** and dispatching them. A **`Handler`** is bound to a Looper and is how you put a message on. That is the whole mechanism.

```kotlin
// This is what the main thread is doing, forever.
Looper.prepare()
val queue = MessageQueue()
while (true) {
    val message = queue.next()   // blocks until something arrives, or a delay expires
    message.target.dispatchMessage(message)
}
Looper.loop()
```

`ActivityThread.main()` sets this up and calls `Looper.loop()`, which never returns. So the main thread is not "running your app" — it is sitting in a loop, and your `onCreate`, your click listener, your frame callback are all *messages that were dispatched to it*.

Two consequences fall directly out of that:

**Ordering, not concurrency.** Messages run one at a time, in order (with delayed ones ordered by their due time). There is no interleaving, so no lock is needed. A `post {}` does not run "in parallel"; it runs *after* whatever is currently running finishes.

**Blocking is total.** A message that takes 500 ms blocks every other message for 500 ms — including the frame callback. This is why `View` methods throw `CalledFromWrongThreadException` off the main thread: the whole safety argument rests on there being exactly one toucher.

`postDelayed` is the origin of a common leak: a `Handler` holds its `Runnable`, the `Runnable` holds your Activity, and a queued message keeps both alive until it fires. Cancel in `onStop`, or use a coroutine whose scope is cancelled for you.

## The frame budget

The single most useful number in Android performance, and everything in chapters 8 and 11 is downstream of it.

The display refreshes at a fixed rate. At 60 Hz a new frame is needed every **16.6 ms**; at 120 Hz, every **8.3 ms**. `Choreographer` receives a vsync signal from the display and posts the frame work — input, animation, measure, layout, draw — onto the main thread's queue.

The arithmetic is unforgiving and worth internalising: at 60 Hz you have 16.6 ms for *everything* — your callback, measure, layout, draw, and handing the result to the RenderThread. A 40 ms main-thread call does not make one frame late; it eliminates two, and the user perceives a jump rather than a slowdown.

This is why "it feels fast on my Pixel" is not evidence. A flagship absorbs sloppiness that a mid-range device turns into visible stutter, which is chapter 11's argument for profiling release builds on cheap hardware.

A **RenderNode** holds a recorded display list plus properties — position, alpha, transform. The important consequence: changing a *property* does not require re-recording. Animating `translationX` or `alpha` on a `View`, or using `graphicsLayer` in Compose, updates a RenderNode property and skips draw entirely. Animating by changing layout parameters does not, which is why the two feel different at the same frame rate.

**SurfaceFlinger** composites the windows of every visible app. Where it can, the display hardware composites directly through an **overlay**, with no GPU work at all. Buffer queues plus triple buffering give one frame of slack — which is why a single slow frame sometimes shows nothing and two in a row always do.

## Where frames are lost

Ranked by how often they turn out to be the cause.

**Main-thread stalls.** Anything from chapter 12 — I/O, a Binder call, lock contention — inside the frame budget. Still the most common by a distance.

**Layout thrash.** A `requestLayout` per item per frame, usually from a setter called during bind.

**Overdraw.** Painting the same pixel several times: a window background under an opaque container under an opaque card. The GPU debug overlay shows it in colour; two layers is usually fine, four is not.

**Large bitmap uploads.** A texture upload on first display of a big image blocks the RenderThread. Chapter 17 sizes bitmaps to the view.

**GC pauses.** Allocation inside `onDraw` or a per-frame lambda. Sixty frames a second of garbage produces collections at exactly the wrong moment.

**Cold shader compilation.** The first time a particular drawing operation runs, its shader is compiled — visible as jank on the very first scroll or first screen, and never again. This is what **Baseline Profiles** address (ch. 2, ch. 11): the work is done before the user's first launch.

## Measuring rather than guessing

Every claim in this chapter is checkable, and chapter 11 makes that a CI gate.

```bash
adb shell dumpsys gfxinfo <pkg>                # aggregate: janky frame percentage
adb shell dumpsys gfxinfo <pkg> framestats     # the last 120 frames, per stage, in ns
```

`framestats` is the highest-value output here. Each row is one frame with timestamps for input, animation, traversal, draw, sync, GPU and swap. Subtracting adjacent columns tells you *which stage* was slow, which immediately separates "my code is slow" from "the GPU is the bottleneck".

**Perfetto** shows the same thing as a timeline, with the main thread and RenderThread side by side, so a frame blocked on the RenderThread is visually obvious. **JankStats** reports jank from real devices in the field, which is the only way to learn about the hardware you do not own. **"Profile HWUI rendering"** in developer options draws per-frame bars live — coarse, but it finds a regression in seconds.

## Why Compose exists

With the pipeline in hand, the motivation is concrete rather than fashionable.

**Inflation is parsing at runtime.** Every XML layout is parsed and reflected into objects on the main thread, on first use.

**Deep hierarchies multiply measure passes,** as above, and the View system's answer — `ConstraintLayout` — is a flat hierarchy with a constraint solver, which is a workaround rather than a fix.

**Mutable view state means the source of truth is the view tree.** You set text on a view, and now the view holds state your model does not. Keeping them in sync by hand is where a large share of UI bugs live.

**Nothing knows what changed.** A View has no idea which of its properties depend on which data, so invalidation is manual and either too broad (jank) or too narrow (stale UI).

Compose changes exactly these four: no inflation (composables are functions), a single measure pass by contract, state that the runtime *observes*, and invalidation computed from what was actually read. Chapter 13 shows the machinery. What it does not change is anything to the right of your process in the diagram above — the RenderThread, SurfaceFlinger and the 16.6 ms are identical.

## Declarative vs imperative

In the View world you *mutate*: find a view, set its text. The view tree is the source of truth, and keeping it in sync with your data is your job (ch. 8, ch. 8).

In Compose you *describe*: given this state, the UI looks like this. The runtime compares descriptions and applies the difference.

```kotlin
@Composable
fun Counter(count: Int, onIncrement: () -> Unit) {
    Button(onClick = onIncrement) { Text("Tapped $count times") }
}
```

There is no `setText`. When `count` changes the function runs again, produces a different description, and the runtime updates the one thing that differs.

What that buys: no possible desync between model and view, and invalidation computed rather than hand-written. What it costs: your function may run **many times a second**, so it must be cheap and it must be safe to run repeatedly — which is the source of most of the rules below.

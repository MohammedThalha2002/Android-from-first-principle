What should the app show when the network is gone? **Everything.**

Not a spinner, not an error screen — the content the user had a moment ago, plus the ability to keep working. That is achievable, and the design that achieves it is a single inversion of the usual data flow.

This is the hardest correctness problem in client engineering, because it is a distributed-systems problem wearing a mobile app's clothes: two replicas, an unreliable link, concurrent writes on both sides, and a user who will judge you on whether their edit survived.

## Local as the source of truth

The inversion, stated plainly: **reads always come from disk. The network is a writer to the local store, never something the UI waits for.**

## Read strategies

Given local-first, the question becomes when to refresh — and what to show while you do.

| Strategy | Behaviour | Fits |
|---|---|---|
| Cache-then-network | show local, fetch, update | almost everything |
| Stale-while-revalidate | same, plus an explicit freshness signal | content where age matters |
| Network-only | no local copy | payment confirmation, one-time codes |

**Store freshness, not just data.** A `syncedAt` per record or per collection is what lets you decide whether to refresh and what lets you be honest with the user:

```kotlin
@Entity data class ArticleEntity(/* ... */, val syncedAt: Long)
```

**Showing stale data with an honest indicator** beats both alternatives. Hiding staleness means the user acts on old information; blocking on refresh throws away the reason for having a local store. A quiet "Updated 2 hours ago" or an offline chip respects the user's judgement.

## Write strategies

Reads are the easy half. Writes are where the correctness problem is.

**Write-through** — write locally and remotely together, failing if the network fails. Simple, and it means no offline writes, so it is not offline-first.

**Write-back with an outbox** is the real pattern. The local write succeeds immediately; a durable queue of pending mutations drains when the network allows.

```kotlin
@Entity data class PendingMutation(
    @PrimaryKey(autoGenerate = true) val localId: Long = 0,
    val kind: String,               // "create" | "update" | "delete"
    val entityId: String,
    val payload: String,
    val idempotencyKey: String,     // stable across retries (ch. 16)
    val createdAt: Long,
    val attempts: Int = 0,
)
```

The properties that matter:

**Durable.** The outbox is a table, so a pending write survives process death (ch. 5) and reboot. An in-memory queue loses the user's edit exactly when they least expect it.

**Ordered.** Drain in creation order per entity. Applying a delete before its create leaves an orphan on the server.

**Idempotent.** The key is generated once and stored, so a retry after an ambiguous failure — the request succeeded but the response was lost — does not duplicate (ch. 16).

**Optimistic UI with rollback.** Apply the change locally at once, mark it pending, and reconcile when the server answers:

```kotlin
suspend fun rename(id: String, title: String) {
    dao.update(id, title, pending = true)                       // instant
    outbox.enqueue(Rename(id, title, idempotencyKey = uuid()))  // durable
}
```

On permanent failure — a `4xx`, not a timeout — revert the local change and **tell the user**. A silent rollback is worse than an error: they saw it succeed.

## Conflict resolution

Two replicas, both edited, one link. Something has to give.

| Strategy | How | When it fits |
|---|---|---|
| Last-write-wins | latest timestamp wins | low-stakes, single-user data |
| Server-authoritative | server state always wins | the server has rules the client cannot know |
| Per-field merge | merge non-overlapping fields | documents with independent fields |
| ETag / version | reject a stale write, client re-applies | anything with real value |
| CRDT | mathematically convergent types | collaborative editing |

**Last-write-wins loses data silently**, and "latest" depends on clocks you do not control — device clocks are wrong, sometimes by years. If you use it, use the *server's* clock.

**Version checks are the honest default for data that matters.** Send the version you read; the server rejects if it moved:

```
PUT /articles/42
If-Match: "v7"
→ 412 Precondition Failed        # someone else changed it; refetch and decide
```

**CRDTs, honestly:** conflict-free replicated data types converge without coordination, and they are the right answer for collaborative editing. For a typical app they are substantial complexity for a problem a version check solves. Reach for them when concurrent editing of the same field is the product, not an edge case.

**Surface the conflict when the data deserves it.** A user's long note, silently overwritten, is data loss. Keeping both and asking is sometimes the only correct answer.

## Sync mechanics

**Full versus delta.** Full sync is simple and gets expensive as data grows. Delta sync asks "what changed since token X" and returns a new token:

```kotlin
suspend fun delta() {
    var cursor = syncState.cursor()
    do {
        val page = api.changes(since = cursor, limit = 200)
        db.withTransaction {                       // page and cursor commit together
            dao.upsert(page.items.map(::toEntity))
            dao.deleteAll(page.deletedIds)
            syncState.setCursor(page.nextCursor)
        }
        cursor = page.nextCursor
    } while (page.hasMore)
}
```

The cursor must be committed **in the same transaction** as the data. Otherwise a crash between them means either replaying a page or, worse, skipping one.

**Push-triggered sync.** FCM (ch. 9) as a "come and get it" signal, not as data. The push wakes the app, the app fetches authoritative state. Sending business data in a push payload eventually corrupts state, because pushes are lossy, unordered and size-limited.

**Scheduling with WorkManager** (ch. 9) — durable, constraint-aware, survives reboot:

```kotlin
val work = PeriodicWorkRequestBuilder<SyncWorker>(6, TimeUnit.HOURS)
    .setConstraints(Constraints.Builder()
        .setRequiredNetworkType(NetworkType.CONNECTED)
        .setRequiresBatteryNotLow(true)
        .build())
    .setBackoffCriteria(BackoffPolicy.EXPONENTIAL, 30, TimeUnit.SECONDS)
    .build()
WorkManager.getInstance(ctx).enqueueUniquePeriodicWork("sync", KEEP, work)
```

Unique work with `KEEP` is what prevents fifty scheduled syncs after fifty app launches.

## Observing the network

**"isConnected" lies.** A device connected to Wi-Fi with no internet, a captive portal (ch. 16), or a VPN that is up but routing nowhere all report connected. What you want is `NET_CAPABILITY_VALIDATED` — the system actually reached the internet:

```kotlin
val request = NetworkRequest.Builder()
    .addCapability(NetworkCapabilities.NET_CAPABILITY_INTERNET)
    .addCapability(NetworkCapabilities.NET_CAPABILITY_VALIDATED)
    .build()
```

Even then, **treat connectivity as a hint, not a gate.** Do not check before acting; act, and handle failure. The check is racy — the network can drop between the check and the request — and a request that fails is information you needed anyway. Use connectivity to *trigger* a drain, not to decide whether to try.

`NET_CAPABILITY_NOT_METERED` is the check that should gate a large download.

## Consistency in the UI

The bug that appears in every offline-first app on the first sync after an offline edit: **the item flickers back**.

The user renames something offline. The local row updates. A sync arrives with the server's copy — which does not have the rename yet, because the outbox has not drained. The UI reverts, then flips forward again when the write lands.

The fix is to **never let a server snapshot overwrite a locally pending change**:

```kotlin
suspend fun applyServer(items: List<Entity>) = db.withTransaction {
    val pending = outbox.pendingEntityIds().toSet()
    dao.upsert(items.filterNot { it.id in pending })   // pending rows keep their local value
}
```

**Stable identity across the boundary** is the other half. An item created offline has no server id yet, so it needs a client-generated one — a UUID — that survives the round trip, with the server either adopting it or returning a mapping you apply in one transaction. Using a temporary negative id and swapping it later produces a moment where the UI's key changes, which breaks list animations (ch. 8, ch. 13) and scroll position.

## Testing sync

Sync is exactly the code that "works on my machine" and fails on a train. It has to be tested deterministically.

**A fake server with controllable latency and failure** lets you write the cases that matter: request succeeds but the response is lost, connectivity drops mid-drain, a conflicting edit arrives.

```kotlin
@Test fun `a write survives an ambiguous failure without duplicating`() = runTest {
    server.failNextWith(SocketTimeoutException())   // request arrived, response lost
    repo.rename("1", "New")
    syncer.drain()                                   // retries with the SAME idempotency key
    syncer.drain()
    assertEquals(1, server.appliedMutations.size)
}
```

**Property-style tests over orderings** are worth the effort here: generate a set of offline operations, apply them in every order, and assert the final state converges. That is how you find the ordering bug that only occurs when a delete drains before its create.

**Simulate offline in instrumented tests** with `svc data disable` / `svc wifi disable`, so airplane-mode behaviour is a test rather than a manual ritual.

## Failure modes: Offline-first & sync

**An offline edit is lost.** *Symptom:* rare complaints of a change that "did not save". *Cause:* the mutation queue was in memory and the process died (ch. 5). *Fix:* a durable outbox table.

**A duplicate is created after a flaky connection.** *Symptom:* two records from one action. *Cause:* a retried write with a fresh idempotency key, or none. *Fix:* generate the key once, store it with the mutation.

**An item flickers back to its old value after sync.** *Symptom:* an edit reverts, then reappears. *Cause:* a server snapshot overwriting a pending local change. *Fix:* exclude pending ids when applying server state.

**Sync runs constantly and drains the battery.** *Symptom:* Play Console flags excessive wakeups. *Cause:* work enqueued per launch instead of unique periodic work, or no constraints. *Fix:* `enqueueUniquePeriodicWork` with `KEEP`, plus network and battery constraints (ch. 9).

**Data is skipped after a crash mid-sync.** *Symptom:* records missing until a full resync. *Cause:* the cursor was committed separately from the page. *Fix:* one transaction.

**Everything is stale on a hotel Wi-Fi.** *Symptom:* the app believes it is online and every request fails oddly. *Cause:* a captive portal, and a connectivity check that only asked for `INTERNET`. *Fix:* require `NET_CAPABILITY_VALIDATED`; treat connectivity as a hint.

**A user's edit is silently overwritten by another device.** *Symptom:* work disappears, no error. *Cause:* last-write-wins on a device clock. *Fix:* version or ETag checks; surface the conflict.

## Cheat-sheet: Offline-first & sync

```kotlin
// reads never touch the network
fun items(): Flow<List<Item>> = dao.observeAll().map { it.map(Entity::toDomain) }

// writes: local now, durable queue, drain later
dao.update(id, value, pending = true)
outbox.enqueue(Mutation(id, value, idempotencyKey = uuid()))

// applying server state without clobbering pending local edits
dao.upsert(serverItems.filterNot { it.id in outbox.pendingEntityIds() })

// cursor and data commit together, or not at all
db.withTransaction { dao.upsert(page.items); syncState.setCursor(page.next) }
```

```bash
adb shell am kill <pkg>            # prove the outbox survived (ch. 5)

```

| Decision | Default |
|---|---|
| reads | local store only |
| writes | optimistic local + durable outbox |
| retries | idempotency key, generated once |
| conflicts | version/ETag; surface it if the data matters |
| connectivity | a hint that triggers a drain, never a gate |
| scheduling | unique periodic work with constraints |

## Paging as a protocol

Pagination is a contract with the server, and the two common shapes differ in a way that matters on a mutating list.

**Offset paging** — `?offset=40&limit=20` — is simple and **wrong on data that changes**. Between fetching page 2 and page 3, someone inserts an item at the top. Every subsequent row shifts down one, so the item that was at offset 60 is now at 61: the user sees a **duplicate** at the page boundary. Delete an item instead and one is **skipped entirely** — silently, with no error anywhere.

**Keyset (cursor) paging** — `?after=<opaque cursor>&limit=20` — asks for what comes after a specific item. Inserts and deletes elsewhere do not shift the anchor, so the boundary stays correct. It is also faster on the server, because the database can seek an index rather than counting past `OFFSET` rows (ch. 15).

Use keyset paging for anything that changes. Offset is acceptable for genuinely static, ordered data.

## Paging 3

The library exists because doing this correctly by hand — loading, appending, retrying, deduplicating, surviving rotation — is more work than it looks.

```kotlin
class ArticleSource(private val api: Api) : PagingSource<String, Article>() {
    override suspend fun load(params: LoadParams<String>): LoadResult<String, Article> = try {
        val page = api.articles(after = params.key, limit = params.loadSize)
        LoadResult.Page(page.items, prevKey = page.prevCursor, nextKey = page.nextCursor)
    } catch (e: CancellationException) { throw e          // ch. 12
    } catch (e: IOException) { LoadResult.Error(e) }

    override fun getRefreshKey(state: PagingState<String, Article>) =
        state.anchorPosition?.let { state.closestItemToPosition(it)?.id }
}
```

`getRefreshKey` is the one people get wrong: on refresh it decides where to resume, so returning null sends the user back to the top of the list after every refresh.

**`RemoteMediator` is what makes paging offline-first** (ch. 17). Room is the `PagingSource`; the mediator fetches from the network and *writes into the database* when the list runs out:

```kotlin
override suspend fun load(loadType: LoadType, state: PagingState<Int, ArticleEntity>): MediatorResult {
    val cursor = when (loadType) {
        REFRESH -> null
        PREPEND -> return MediatorResult.Success(endOfPaginationReached = true)
        APPEND -> keyDao.next() ?: return MediatorResult.Success(true)
    }
    val page = api.articles(after = cursor)
    db.withTransaction {                                    // page and key together (ch. 17)
        if (loadType == REFRESH) { dao.clearAll(); keyDao.clear() }
        dao.upsert(page.items.map(::toEntity))
        keyDao.set(page.nextCursor)
    }
    return MediatorResult.Success(endOfPaginationReached = page.nextCursor == null)
}
```

The UI never observes the network — it observes Room, exactly as chapter 17 requires.

**`LoadState`** drives the UI: separate states for refresh, prepend and append, each of which can be loading, error or idle. A retry belongs at the point of failure — a footer for a failed append, a full-screen state for a failed refresh — not one generic error for all three.

**Placeholders** show the right scroll extent before data arrives, which keeps the scrollbar honest and prevents the list jumping. They need a known total count and null-tolerant binding; without a count, turn them off.

**Test a `PagingSource` directly** — it is an ordinary suspend function returning a value, so no UI is required.

## List performance

Chapters 8 and 13 covered the mechanisms; this is the checklist.

**Stable keys.** `key` in `LazyColumn`, `setHasStableIds` with a `RecyclerView`. Without them an insert invalidates everything below it.

**Content types.** `contentType` partitions the reuse pool so a header is never reused as a row.

**Stable item size.** A view whose height changes on bind forces a layout pass every frame (ch. 8). Reserve space for images with a fixed aspect ratio rather than letting the row resize when the bitmap arrives.

**Never nest the same scroll axis.** A vertical list inside a vertical scroller either throws or composes every item, defeating laziness entirely.

**Prefetch distance** trades memory for smoothness. The defaults are reasonable; increase only with a measurement showing you need it.

**Measure with Macrobenchmark** (ch. 11), because scroll performance is exactly the thing intuition gets wrong:

```kotlin
@Test fun scrollFeed() = benchmarkRule.measureRepeated(
    packageName = "dev.firstprinciples.android",
    metrics = listOf(FrameTimingMetric()),
    compilationMode = CompilationMode.Partial(),      // realistic: a Baseline Profile applied
    startupMode = StartupMode.WARM,
    iterations = 10,
) { /* fling the list */ }
```

## Failure modes: Paging, lists & media

**`OutOfMemoryError` when opening a photo.** *Symptom:* crashes concentrated on devices with smaller heaps. *Cause:* decoding at full resolution — 48 MB for a 12 MP image. *Fix:* decode at target size; consider `RGB_565` or `HARDWARE`.

**The list scrolls smoothly, then re-downloads everything.** *Symptom:* network traffic on every scroll pass. *Cause:* an unstable request key or size, or an undersized disk cache. *Fix:* stable URL and size; check the cache stats.

**Duplicate or missing rows at a page boundary.** *Symptom:* an item appears twice, or vanishes. *Cause:* offset paging on mutating data. *Fix:* keyset pagination.

**Refresh sends the user back to the top.** *Symptom:* pull-to-refresh loses the scroll position. *Cause:* `getRefreshKey` returning null. *Fix:* anchor on the closest item.

**The camera preview freezes after a few seconds.** *Symptom:* analysis stops, preview stalls. *Cause:* `ImageProxy` not closed, exhausting the buffer queue. *Fix:* close in a `finally`; use `KEEP_ONLY_LATEST`.

**Audio stops when the app is backgrounded.** *Symptom:* playback ends on leaving the app. *Cause:* no foreground service. *Fix:* `MediaSessionService` with the `mediaPlayback` type (ch. 9).

**Rows jump as images load.** *Symptom:* the list shifts while scrolling. *Cause:* item height depending on the image. *Fix:* a fixed aspect ratio, so space is reserved before the bitmap arrives.

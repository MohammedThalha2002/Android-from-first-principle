## The traversal

Rendering a frame walks the view tree three times, in order, and each pass has a different job.

**Measure** asks every view how big it wants to be, given constraints from its parent. **Layout** assigns each view a position and final size. **Draw** records the drawing commands. Only after all three does anything reach the screen.

The cost that surprises people is that **measure can run your children more than once**. A parent that cannot decide a child's size in one attempt measures it, looks at the result, and measures again with different constraints. `RelativeLayout` does this by construction. A `LinearLayout` with weights measures twice. And a `MATCH_PARENT` child inside a `WRAP_CONTENT` parent is a genuine contradiction — the parent's size depends on the child's, and the child's depends on the parent's — resolved by measuring twice.

Nest those and it multiplies. Three levels of double-measuring is eight measure passes per view, which is where the old advice to keep hierarchies flat comes from. It was never about the number of objects; it was about the exponent.

## `MeasureSpec`

The measure pass is a **two-way negotiation**, and `MeasureSpec` is its vocabulary. A parent packs a mode and a size into a single int and hands it down; the child replies with the size it wants.

| Mode | The parent is saying | Comes from |
|---|---|---|
| `EXACTLY` | you will be this size | `match_parent`, a fixed dp |
| `AT_MOST` | you may be up to this size | `wrap_content` |
| `UNSPECIFIED` | tell me what you want, no limit | a scrolling parent measuring a child |

`UNSPECIFIED` is where custom views break. A `RecyclerView` measuring an item vertically passes `UNSPECIFIED` for height, and a custom view that treats that size as a real bound will compute a height of zero and vanish. The rule for `onMeasure` is to handle all three modes explicitly and always finish by calling `setMeasuredDimension`.

## Invalidation

Two methods, wildly different costs, and choosing wrong is a common cause of scroll jank.

**`invalidate()`** says "my appearance changed". It schedules a **draw** pass for that view. Cheap — the layout is untouched.

**`requestLayout()`** says "my size might have changed". That cannot be answered locally, so it walks **up to the root** and schedules a full measure and layout pass for the whole tree.

```kotlin
// Colour change: nothing moved.
fun setHighlighted(on: Boolean) { highlighted = on; invalidate() }

// Text change: the view may need to be wider, so the whole tree re-measures.
fun setLabel(value: String) { label = value; requestLayout(); invalidate() }
```

In a scrolling list this is the difference between smooth and not. A `requestLayout` from a bind callback triggers measure and layout for everything on screen, every frame, while the finger is moving. Many framework setters call `requestLayout` internally — `setText` does — which is why changing text during a scroll is more expensive than it looks.

## Windows, surfaces &amp; insets

A **window** is the unit SurfaceFlinger composites — not a View. Your Activity has one; a dialog gets another; the status bar and navigation bar are windows owned by the system.

Because system bars are separate windows drawn over yours, your content can be underneath them. **Insets** describe those overlaps. `WindowInsets` reports several kinds — system bars, the IME, display cutouts — and Compose exposes them as `safeDrawing` (avoid anything drawn over) and `safeContent` (also avoid gesture areas).

Android 15 <ApiLevel changedIn="35" /> **enforces edge-to-edge** for apps targeting it: your content draws behind the bars whether you asked or not, so unhandled insets become clipped content rather than a stylistic choice. The fix is to consume insets at the right level, which chapter 19 covers with the rest of adaptive layout.

Three surface types, for when the normal path is not enough:

- **`SurfaceView`** — its own surface, composited independently, so video or a game renders without going through your view hierarchy. It does not transform or animate with the rest of the UI.
- **`TextureView`** — behaves like a normal view (transforms, alpha) at the cost of an extra copy through the GPU.
- **`SurfaceControl`** — direct control over a surface, for advanced cases.

## Failure modes: Rendering pipeline

**A list stutters on first scroll and never again.** *Symptom:* jank on the first pass through a screen. *Cause:* cold shader compilation. *Fix:* ship a Baseline Profile (ch. 11); confirm by scrolling twice in a trace.

**Scrolling is smooth on a flagship, janky on a mid-range phone.** *Symptom:* reports you cannot reproduce. *Cause:* main-thread work inside the budget, absorbed by a faster CPU. *Fix:* profile a release build on cheap hardware; `framestats` rather than intuition.

**Every frame runs a full layout pass while scrolling.** *Symptom:* traversal dominates the trace. *Cause:* a `requestLayout` from bind — often `setText` or a size-affecting setter. *Fix:* set values that do not change size, or keep the item size stable.

**Content sits under the status bar on Android 15.** *Symptom:* a clipped header after a `targetSdk` bump. *Cause:* enforced edge-to-edge. *Fix:* consume `safeDrawing` insets (ch. 19).

**An animation is smooth in one place and janky in another.** *Symptom:* identical duration, different feel. *Cause:* one animates RenderNode properties, the other changes layout. *Fix:* animate `translation`/`alpha`/`graphicsLayer`, not layout params.

**A custom view has zero height inside a `RecyclerView`.** *Symptom:* invisible in a list, correct elsewhere. *Cause:* `onMeasure` treated `UNSPECIFIED` as a bound of zero. *Fix:* handle all three modes.

## The View hierarchy

A `View` is a rectangle that measures, lays out, draws and handles touch. A `ViewGroup` is a `View` that also positions children. Everything on screen in the old toolkit is one of those two.

**`LayoutParams`** are the child's instructions *to its parent*, which is why `layout_width` lives on the child but is interpreted by the parent, and why the wrong parent type silently ignores attributes it does not understand — `layout_weight` in a `FrameLayout` does nothing at all.

**Inflation is parsing at runtime** (ch. 8). `LayoutInflater` reads compiled XML, reflects to construct each view, applies attributes, and repeats. It is main-thread work proportional to the number of views, and it is the single biggest cost when a screen first appears.

Three tools reduce it:

- **`<merge>`** — when your layout's root would be a redundant container inside its parent, `<merge>` removes that level entirely.
- **`<include>`** — reuse without copying.
- **`ViewStub`** — a zero-size placeholder that inflates only when shown. The right answer for an error state or an empty view that most users never see.

**The styles cascade** resolves in a fixed order: an attribute set directly on the view beats a `style`, which beats the theme, which beats the parent theme. `?attr/colorPrimary` reads from the theme at inflation time, which is how one layout serves light and dark (ch. 19). Getting a "wrong colour" is nearly always a view inflated with a `Context` whose theme is not the one you expected.

## ConstraintLayout as a flat-hierarchy tool

`ConstraintLayout` exists because of chapter 8's exponent: nesting multiplies measure passes, so the fix is not to nest.

Each child declares constraints relative to its siblings or the parent, and a solver computes positions in — usually — a single pass. A screen that needed four nested `LinearLayout`s becomes one flat container.

**Chains** distribute several views along an axis (spread, spread-inside, packed) — the replacement for weights. **Guidelines** are invisible anchors at a percentage or fixed offset. **Groups** toggle visibility of several views by id, without a wrapper that would reintroduce nesting. `Barrier` constrains to whichever of several views is largest, which is the clean fix for labels that change length across locales (ch. 19).

`MotionLayout` extends it with keyframed transitions between two constraint sets. It is genuinely capable and genuinely hard to debug; for anything beyond a well-defined transition, a Compose animation is easier to reason about.

## RecyclerView internals

The most important class in the old toolkit, and the one whose internals most repay understanding.

The split is deliberate. **Adapter** creates and binds; **ViewHolder** caches the results of `findViewById` for one item; **LayoutManager** decides positions; **Recycler** owns reuse.

Reuse has two levels, and they are not the same:

- The **scrap** holds views detached during the current layout pass — reattached without rebinding if they have not changed.
- The **pool** holds views scrolled off-screen, keyed by view type. Taken from the pool, a view is **rebound** but not re-inflated.

That is where the performance comes from: inflation happens roughly as many times as there are visible items plus a few, not once per item in a list of ten thousand.

**`DiffUtil`** computes the minimum set of changes between two lists so you can animate rather than call `notifyDataSetChanged`, which rebinds everything and loses scroll position. `ListAdapter` wraps `AsyncListDiffer` and moves the diff to a background thread; `submitList` is then the only update path you need.

**Stable IDs** let the adapter track an item across a diff, which is what makes move animations correct. Without them a moved item is an insert plus a delete.

**"The list stutters on first scroll"** has a small set of causes, worth knowing as a checklist: inflation of the first screenful (prefetch helps, and `setInitialPrefetchItemCount` for nested lists), oversized bitmaps decoded on bind (ch. 17), `requestLayout` from a setter during bind (ch. 8), and a shared pool missing between nested `RecyclerView`s so the inner ones each inflate their own.

```kotlin
// Compose equivalent — the same reuse, with keys instead of stable IDs.
LazyColumn {
    items(articles, key = { it.id }, contentType = { it.kind }) { ArticleRow(it) }
}
```

`key` is `setHasStableIds`. `contentType` is the view type that partitions the pool. The mechanism is the same; the bookkeeping is not yours.

## Custom views

Three methods, and the contracts matter more than the code.

**`onMeasure`** must handle all three `MeasureSpec` modes (ch. 8) and must end by calling `setMeasuredDimension`. **`onLayout`** positions children, and only a `ViewGroup` needs it. **`onDraw`** paints — and must **allocate nothing**, because it runs up to sixty times a second. Create `Paint` and `Path` objects as fields.

```kotlin
class Meter(context: Context, attrs: AttributeSet?) : View(context, attrs) {
    private val paint = Paint(Paint.ANTI_ALIAS_FLAG)   // allocated once
    private var value = 0f

    fun setValue(v: Float) { value = v; invalidate() }  // appearance only — see ch. 8

    override fun onDraw(canvas: Canvas) {
        paint.color = trackColor
        canvas.drawRect(0f, 0f, width * value, height.toFloat(), paint)
    }
}
```

**Saving state.** A custom view with internal state must implement `onSaveInstanceState`/`onRestoreInstanceState` and needs an **id** in the layout, because the framework saves view state keyed by id. A view without one is silently not saved — one of the quieter ways state is lost on rotation (ch. 5).

**Touch handling** goes through `onTouchEvent` and `MotionEvent`. Use `ViewConfiguration` for thresholds rather than inventing constants: `scaledTouchSlop` is how far a finger may move before it is a scroll rather than a tap, and it differs by device density. `GestureDetector` handles the common gestures so you do not re-derive them.

**Accessibility** is not automatic for a custom view. The framework cannot know what your drawing means, so you supply it — `contentDescription`, and an `AccessibilityDelegate` for anything interactive. Chapter 19 treats this properly; the point here is that a custom view is where accessibility is most often silently dropped.

## Binding &amp; the death of `findViewById`

`findViewById` returns a platform type (ch. 12) with no compile-time check that the id exists in *this* layout — so a wrong id compiles and throws.

**ViewBinding** generates a class per layout with a typed, non-null field per id. It is the current recommendation: no annotation processing, no build-time cost worth mentioning, and it turns both failure modes into compile errors.

**DataBinding** put expressions in XML. It is no longer recommended: logic in XML is not testable or debuggable, and it adds an annotation processor to your build (ch. 20). Migrate away from it where you can; do not add it.

The **binding leak** is the same one as chapter 5, and it is worth repeating because it is the single most common leak in Fragment code: a Fragment outlives its view, so a binding held in a Fragment field keeps a destroyed view tree alive. Null it in `onDestroyView`.

## Interop with Compose

Both directions work, and incremental migration is the realistic path for an existing app.

**`ComposeView` in XML** — put a Compose subtree inside a View layout:

```kotlin
binding.composeHost.setContent { ArticleHeader(state) }
```

**`AndroidView` in Compose** — put a View inside a composable, for a `MapView`, a `SurfaceView`, or an in-house widget not worth porting yet:

```kotlin
AndroidView(
    factory = { context -> MapView(context) },   // called once
    update = { it.setCenter(center) },           // called on every recomposition
)
```

Keep `factory` cheap and `update` idempotent; `update` runs whenever a state it reads changes.

Two boundary problems are worth knowing before you hit them. **Nested scrolling** across the boundary needs cooperation — a Compose scrollable inside a View scroller needs `rememberNestedScrollInteropConnection()`, or the two fight. And **theme bridging**: Compose does not read your XML theme, so colours diverge unless you map them deliberately. Chapter 19's advice — semantic tokens in one place, consumed by both — is what prevents a half-migrated app looking half-migrated.

**A migration strategy that works:** migrate leaf-first, screen by screen, behind a flag. New screens in Compose; existing screens converted when you are already changing them. Do not convert a working screen for its own sake, and do not attempt a whole-app rewrite — the intermediate state lasts longer than anyone plans for, so it has to be a state the app can ship in.

## Failure modes: Views & XML

**A view's state is lost on rotation, but only that view.** *Symptom:* one custom widget resets while the rest of the screen restores. *Cause:* no `android:id`, so the framework had no key to save under. *Fix:* give it an id and implement the save/restore pair.

**Memory grows with every navigation.** *Symptom:* heap climbs, LeakCanary points at a Fragment's view. *Cause:* a binding or view reference in a Fragment field. *Fix:* null it in `onDestroyView` (ch. 5).

**`notifyDataSetChanged` loses scroll position and flickers.** *Symptom:* the list jumps on every update. *Cause:* the whole adapter invalidated. *Fix:* `ListAdapter` with `submitList`, plus stable IDs.

**Nested lists stutter and allocate.** *Symptom:* an inner horizontal list in a vertical one is janky. *Cause:* each inner list has its own pool, so nothing is reused across them. *Fix:* a shared `RecycledViewPool`, and `setInitialPrefetchItemCount`.

**Colours are wrong in one place only.** *Symptom:* a dialog or a dynamically added view ignores the theme. *Cause:* inflated with the wrong `Context` — application instead of themed activity. *Fix:* inflate with the Activity or a `ContextThemeWrapper`.

**Compose and XML parts of one screen do not match.** *Symptom:* different greys either side of a boundary. *Cause:* two independent theme definitions. *Fix:* one source of semantic tokens, consumed by both (ch. 19).

## Insets &amp; edge-to-edge

Chapter 8 established that system bars are separate windows drawn over yours. Insets are how you find out where.

The kinds that matter: **system bars** (status, navigation), the **IME** (the keyboard, which animates), and **display cutouts**. Compose composes these into `safeDrawing` — do not draw anything under here — and `safeContent`, which also excludes gesture areas.

```kotlin
Scaffold(modifier = Modifier.fillMaxSize()) { padding ->
    LazyColumn(contentPadding = padding) { /* scrolls under the bars, but ends clear of them */ }
}
```

The distinction that produces good edge-to-edge UI: apply insets as **padding on the scrolling content**, not as a margin on the container. Content then scrolls behind a translucent bar — which is the point of edge-to-edge — while the first and last items are still reachable.

Android 15 <ApiLevel changedIn="35" /> enforces edge-to-edge, so this is no longer optional for apps targeting it: unhandled insets become clipped content.
